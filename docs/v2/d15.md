## 1. What the owner decided

- A **derive / check is per row**. Anything across rows is **just another module** that writes whatever columns it declares (a
  rate with an interval, a mean, a concatenation, a max, a count) into **its own made table**, like every module. Not every number
  needs an average, `lo`, `hi` or a percentile.
- **A (option 2):** a row check makes its rows and nothing else. bitt never adds them up behind your back. To get a rate, run the
  `rate` module over the check's run.
- **B (per unit):** everything counts **per unit** (a row of the dataset / evalset / import the work started from), never per
  distinct input. Storage still dedups: a made row is stored once, however many units share it.

## 2. What exists today (and is wrong)

- `bitt.metric` (src/bitt/tables.py `FIXED`) holds every metric in one fixed shape `{name, value, n, lo, hi, by, …}`;
  `src/bitt/aggregate.py` adds rates and means to every row-check run by default (`tools/run.py` `row_metrics`); a table-scope check
  returns `{name: number}` that becomes `bitt.metric` rows (`aggregate_check`, header `writes: "metrics"`); a train's
  `job.report(...)` values become `bitt.metric` rows with `by = reported` (`tools/run.py`, around `sets.write_metric(... "reported")`);
  an eval's `win` reads `metrics_of(run)[metric][lo|hi|value]` (`tools/pipeline.py` `decide`, `B.metrics`).
- A run over another run reads the input run's **distinct** output rows (`input_of` → its `out_set`, no repeats). A column read from
  further up (`--cols b=tickets.label`) is found by `read_value` walking `__src` upward and taking the **first** hit. So two tickets
  with the same text and different gold labels share one prediction row, the check makes **one** verdict for both, against an
  arbitrary one of the two labels, and the rate counts it once.

## 3. The design to build

### 3.1 Unit-aligned runs
- Every run has a **unit set**: the set of units its work started from. A run whose input is an import, a set, a dataset or an
  evalset: that set is its unit set. A run whose input is another run: the input run's unit set. A **table derive that writes rows**
  (not a select, not an aggregate) starts a new unit set: its own output rows are the units downstream (this already matches
  `run.unit_set`: "made by a table derive").
- A run's **input set and output set are aligned with its unit set**: entry *i* belongs to unit *i*. Samples and parts follow their
  unit in order: unit *i*'s entries are its sample 0..S-1 (each with its parts, part order). So a generate whose recipe has `--samples 3` over 4
  units has an output set of 12 entries.
- **A run's input or output set may list one row many times** (units that read the same values share one stored row). Imports,
  datasets and evalsets keep refusing a row twice (`sets.write_set`, "twice"): give run sets their own kind (`run_in` / `run_out`) and
  allow repeats only for those kinds.
- Record the unit set: a `units` column on `bitt.run` (the unit set hash), and `units` in the run node's payload.
- Ladder rungs and smoke runs stay prefix sets: the first *k* **units** (with all their entries).

### 3.2 Reading along a unit's own chain
- A row module over a run iterates over the **entries** of the input run's output set, not its distinct rows. For entry *i* it reads
  every bound column along **unit *i*'s chain**: the unit row, and entry *i* of each run between the unit set and this one (each run's
  output entry *i*), nearest first. `--cols b=tickets.label` reads `label` from the `tickets` row of that chain: never "the first hit"
  among all rows a shared row came from. Keep the existing errors (no such column; two lines above both have it: bind `line.col`).
- The made row is keyed as today (`in_hash` of the values read, sample, part), so equal values still share one stored row; units with
  different upstream values (the two labels) now get different rows.
- **Lineage is complete in the database:** a made row's `<t>__src` links its direct input row (role = the input table, as now) **and
  every row a bound column was read from** (role = that row's table). A row whose values came from four tickets links all four.

### 3.3 Modules across rows (A)
- A **table-scope check or derive that returns a dict** is an aggregate: `def rate(rows: list, *, …) -> Rate` where `Rate` is a
  `TypedDict` (or `BITT["writes"] = {col: type}`): it writes **exactly one row** with its declared columns into its own made table
  (one table per output contract, as every module), keyed by the input set it read (`h("in", {"set": …})`, linked with role `set`,
  as table derives already are). Rerunning it on the same set reuses that row.
- It receives **one row per entry** of its input run's output set (per unit, per sample, per part) with the bound columns read along
  each unit's chain (3.2), plus `bitt_unit` (the unit row hash) and `bitt_sample`.
- **No defaults:** a row check run writes its verdict rows and no aggregate (delete `row_metrics`, `aggregate.py`, the
  `metrics` run argument, `bitt.metric`, `metrics_of`, `write_metric`, `metric_hash`). The CLI prints rows, never "metric" lines.
- Shipped aggregates (src/bitt/builtins/, standard library only, each standalone):
  - `rate(rows, *, )` over a bool role `x` → `{rate: number, lo: number, hi: number, n: int}` (Wilson 95%; copy the math from
    `aggregate.py` before deleting it)
  - `mean(rows)` over a number role `x` → `{mean, lo, hi, n}` (t interval to 30, normal beyond: as `aggregate.py`)
  - `count(rows)` → `{n: int}`
  - `agreement(rows)` (roles `a`, `b`) → `{agreement: number, kappa: number, n: int}` (it already is a table check; make it write its
    row)
  - remove the old row-scope `rate.py` / `mean.py` (they were per-row identity checks feeding the defaults).

### 3.4 Evals read a row
- An eval's `win` grammar becomes `<column> <op> <number>` (`lo >= 0.5`, `kappa > 0.6`): `column` is a column of the **one row** the
  run its function returns made. Refused when that run made no row or more than one ("the win reads one row: return the aggregate's
  run"), when the column does not exist, or when its value is not a number.
- The decision keeps the whole row it read (`read: {column: value, …}`) and links that run (as now).
- `run.win_clean` keeps one warning: the judged check is a hint in this task (trust). Which check: the module of the run the aggregate
  ran on (its `on`), when that is a check; else the aggregate's own module. Drop the "compares the bare value" warning (bitt cannot know
  which column is a bound).
- Remove `B.metrics`. The plan listener (`pipeline.listen`) is unchanged.

### 3.5 Numbers a train reports
- A train module declares what it reports: `BITT["reports"] = {name: type}` (header.py: validate types like `writes`; no `reports`
  = it reports nothing). `nb_train` declares `{"train_acc": "number", "val_acc": "number", "test_acc": "number"}`.
- At landing, each `job.report(step=…, **values)` line becomes a row in the made table of that contract (`<module>_report`):
  columns `step` (int) + the declared names, keyed by (run, step). A reported name that is not declared fails the landing with a
  clear reason (`next: declare it in BITT["reports"]`). Values stay "reported": never trusted, never a check.

3. **Samples:** 4 units, `--samples 3` on a generate's recipe, then a check and `rate`: `n == 12`.
4. **No defaults:** a row check run makes only its verdict rows (no aggregate row anywhere); `bitt.metric` is not in `tables.FIXED`;
   `git grep -n "metrics_of\|bitt\.metric\|aggregate\." -- src` is empty.
5. **Any columns:** a custom aggregate returning `{"longest": "text"}` runs and stores its one row; an eval whose `win` names
   `longest` is refused ("not a number").
6. **Win reads one row:** an eval whose function returns a row check's run (several rows) is refused with the one-row reason; returning
   the `rate` run decides and keeps `read` = the whole row.
7. **Reuse:** running `rate` again on the same check run makes 0 rows and returns the same row.
8. **Reported:** `nb_train` lands rows in `made.nb_train_report` (`step`, `train_acc`, …); a train module that reports an undeclared
   name fails its landing with the reason.
9. **Rungs:** rung 1 / 5 of a run over a run count units: a rung-5 aggregate has `n == 5` (or 5 × samples).
